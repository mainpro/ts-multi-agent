## 2. 🐞 已识别 Bug 风险

### 2.1 [Critical] EES / unknown-tool-guard 熔断逻辑可能误判合法工具

**位置**: `src/agents/sub-agent.ts:468-482` + `src/agents/unknown-tool-guard.ts`

**现象**:
```typescript
if (!allowedToolNames.has(toolCall.name)) {
  const rewrite = unknownToolGuard.check(toolCall.name);
  if (rewrite) {
    return rewrite;  // 直接返回改写
  }
  return `工具执行失败: 工具 '${toolCall.name}' 不在允许列表中`;
}
```

`UnknownToolLoopGuard.check` 内部用 toolCall.name 做 key 累计,但 `unknownToolGuard.reset()` 只在"合法工具调用"路径调用。如果用户**第一轮**用了 `bash`(合法但不是 safe),SubAgent 拒绝并 +1 计数;第二轮又调 `bash`,计数变为 2;第三轮任何工具都会被熔断(尽管 `bash` 是合法的)。

**影响**: 合法 `bash` 调用偶尔会被熔断,导致 IT 类员工(`bash` 已 enabled)失败。

**修复建议**:
- `UnknownToolLoopGuard` 应只对**真正未在 allowedToolNames 中的名字**计数,合法工具(即使 unsafe)不进入计数路径
- 当前已通过 `allowedToolNames.has` 短路,逻辑上应 OK,但需补回归测试(用 `bash` 连续 5 次调用,验证不熔断)

### 2.2 [Important] `bootstrap-error.test.ts` 测的是 `BootstrapError` 类型但 index.ts 改造后没人触发

**位置**: `__tests__/bootstrap-error.test.ts` + `src/index.ts:80-86, 203-205`

**现象**: 旧的 `process.exit(1)` 已改为 `throw new BootstrapError(...)`,但 `bootstrap()` 在 `app.listen` 之前失败会直接抛到顶层 → Node 进程崩溃并打印 stack,而不是优雅的 BootFailed 消息。

**修复建议**:

- 非 `BootstrapError` 的异常也应打日志而非直接 stack
- 参考 `DEPLOY.md` "故障排查" 一节补全

### 2.3 [Important] 多员工并存:LLM 选错 employeeId / fallback 沉默兜底的风险

**位置**: `src/agents/employee/router.ts:17-32` + `src/routers/intent-router.ts:74-121`

**现象**: `IntentRouter.classify()` 在同一次 LLM 调用中产出 `employeeId`(由 prompt 中 `availableEmployees` 列表引导 LLM 选择)。`routeIntentToEmployee()` 设计上"永不抛错":
- employeeId 缺失 / `registry.has` 为 false → 静默 `defaultFallback()`
- LLM 给的 id 不存在时仅 `log.warn`

这意味着 **LLM 选错 employeeId 不会产生可观测错误**,用户感知的是"答非所问"(兜底员工按 `unrestricted` skill 白名单跑了用户原问)。可能原因:

| 失败模式 | 现象 | 触发条件 |
|---|---|---|
| LLM 漏填 employeeId | 永远走兜底 | 多员工场景,LLM 不确定时省略字段 |
| LLM 幻觉出不存在的 id | 静默兜底 | registry 没列全 / 拼写错误 / 旧 id 残留 |
| LLM 选错相近员工 | 用错误 persona/tools 执行 | 员工边界描述模糊(如多个员工都可处理"合同") |
| prompt 截断导致列表丢失 | 全部走兜底 | 员工列表过长触发 `intentskill-matcher` prompt 超限 |

**影响**: 排障线索只有 `intent-router` 日志 + `employee-router` warn 日志,没有 metric 计数兜底率。

**修复建议**:
- `EmployeeRegistry` 增加 `metrics.fallbackRouted++`(成功 fallback 计数)+ `metrics.invalidEmployeeIdRouted++`(LLM 给的 id 不存在计数),在 `/metrics` 端点暴露
- `IntentRouter` prompt 里给每个员工加 `boundary`(类似 fallback 员工的 `boundaries` 字段)减少边界模糊
- 员工列表超过阈值(暂定 N>5)时考虑 LLM-first 选 employeeId(2 次 LLM)或缩短 brief 字段
- 引入 A/B 测试:让 fallback 员工也带 `metric` 计数,事后分析兜底是否合理

### 2.4 [RESOLVED 2026-08-18] `defaultEmptyEmployee()` 兜底已删除(原 §2.3)

**状态**: ✅ **已删除**(commit `2a972d5`,T5 MainAgent 持 EmployeeRegistry)

**背景**: 旧 MainAgent 构造允许 `options` 为 undefined,内部 fallback 到 `defaultEmptyEmployee()` 工厂返回 `enabled: false` 的 `EmployeeConfig`,仅供测试跳过 persona/skills 路径。生产 bootstrap 加载失败理论上不会走到这里,但缺乏 fail-fast 防护。

**修法**:
- `MainAgentOptions.employee` 字段整体删除
- `MainAgent` 改持 `EmployeeRegistry`(由 bootstrap 注入)
- `defaultEmptyEmployee()` 函数删除
- `MainAgent` 构造无 registry 直接抛 `TypeError`(构造期 fail-fast)
- 测试 helper 全部迁移到 `buildTestMainAgent({ registry })`(`commit 220e4de`,T10 fixture 迁移)

**验证**: `git grep defaultEmptyEmployee` 在 `src/` / `__tests__/` / `docs/` 全部无残留(spec 文件仍引用作为历史档案,不在本检查范围)。

### 2.5 [RESOLVED 2026-08-14] `task-9-summary` 的 `taskResults[0]?.status` 取首个而非最后一个

**状态**: ✅ **已修**(commit `b12a2af`,T6 ResultAggregator 重写)

**位置**: `src/agents/result-aggregator.ts:243`(已替换为 `every(completed)` gate)

修法不仅是改索引,而是整个 rewriter gate 重写:

```typescript
// 旧(bug):
const lastTaskStatus = taskResults[0]?.status ?? 'completed';
if (lastTaskStatus === targetStatus && lastTaskStatus !== 'waiting_user_input') { ... }

// 新(T6):
const completedTasks = taskResults.filter(t => t.status === 'completed');
const failedTasks = taskResults.filter(t => t.status === 'failed');
const waitingTasks = taskResults.filter(t => t.status === 'waiting_user_input');
const allCompleted = completedTasks.length === taskResults.length && waitingTasks.length === 0;
if (this.rewriter && allCompleted) { ... }
```

**影响**: resultRewriter 只在全员 completed 时追加尾注,部分失败或全失败都不追加(由 LLM 摘要 + transfer hook 处理)。同时附带防御纵深:`failedTasks.length > 0` 时强制 `judgment.completed = false`,即使 LLM 误判。

**修复建议**:
```typescript
const lastTaskStatus = taskResults[taskResults.length - 1]?.status ?? 'completed';
```

### 2.6 [Important] `popLastAssistantMessage` 直接重写 L4 文件,无并发保护

**位置**: `src/memory/memory-service.ts:191-216`

```typescript
async popLastAssistantMessage(...) {
  const entries = await this.l4.listEntries(...);
  // ...
  entries.pop();
  await fs.writeFile(filePath, JSON.stringify(...));
}
```

如果两次 `popLast` 并发(同一 session 内),两者都读到完整 entries,各自 pop 末尾 → 文件中最后一条丢失。

**修复建议**:
- 用 SessionStore 的 `writeTimers` 防抖 + 单写者锁(`Map<string, Promise>`)
- 或合并到 `MemoryService.saveAssistantMessage` 的事务里

## 3. ⚡ 性能 / 资源优化

### 3.1 [High] `TaskQueue.findReadyTasks` 每轮全表扫描

**位置**: `src/task-queue/index.ts:428-454`

每次 `processQueue` 都会遍历所有 tasks 找 ready tasks。DAG 规模大时(N=100+)单次调度 O(N),任务图层数 × N → O(N²)。

**修复建议**:
- 维护一个 ready queue(LinkedList),每次 addTask / completeTask 时增量更新
- `removePendingTask` 时同步从 ready queue 移除

---

### 3.2 [High] `SessionStore.saveSession` 100ms 防抖 vs 持久 pending queue

**位置**: `src/memory/session-store.ts:76-94`

防抖 100ms 内高频写入会被合并。如果进程在 100ms 内崩溃,**未触发防抖的 session 修改全部丢失**。

**修复建议**:
- 对 `session.pendingRequests` / `request.tasks` / `request.status` 等"关键路径"用 `flushToDisk`(已部分实现,需扩展覆盖面)
- 或加 WAL(write-ahead log)

---

### 3.3 [High] LLM stream 解析逐 chunk JSON.parse,高 token 流下 CPU 飙升

**位置**: `src/llm/index.ts:725-755`

每条 SSE 事件都 `JSON.parse`,高频 reasoning 流会导致 CPU 100%。

**修复建议**:
- 累计 buffer 解析,每 N 条或 M 字符一次 parse
- 或用 stream-json 库增量解析

---

### 3.4 [Medium] L3 摘要生成是阻塞 LLM 调用

**位置**: `src/memory/memory-service.ts:225-235`

`summarizeRequest` 是 `fireAndForget`,但 LLM 调用本身可能耗时 5-15s。短时间多个请求完成时,会产生 N 个并发 LLM 调用,触发信号量排队(LLM_MAX_CONCURRENT_REQUESTS=20)或直接排队(LLM_MAX_QUEUE_SIZE=50)。

**修复建议**:
- 限速(每秒 ≤2 个摘要生成)
- 或复用 LLM cooldown cache 减少切换延迟

---

### 3.5 [Medium] SessionCache 全量重写磁盘

**位置**: `src/memory/session-store.ts:106-108`

每次 flush 都 `JSON.stringify` 整个 session + 整个文件 `writeFile`。100K 条请求的 session 会写 5MB+ 文件。

**修复建议**:
- 用 append-only 日志 + 定期 snapshot
- 或分文件存储(per-request JSON,目录 `data/memory/{user}/session/{session}/requests/{reqId}.json`)

---

### 3.6 [Medium] `embedding-service` 启动时同步加载模型

**位置**: `src/memory/embedding-service.ts`(未深读,推测)

如果 embedding 是本地模型,启动耗时长(数百 MB 下载/初始化)。

**修复建议**:
- 懒加载(首次 L3 召回时初始化)
- 异步初始化,启动期跳过 L3 摘要生成

---

### 3.7 [Low] 每次 `SkillRegistry.getAllMetadata()` 都 shallow copy

**位置**: `src/skill-registry/index.ts:223-227`

```typescript
return Array.from(this.metadataCache.values())
  .filter(entry => !entry.metadata.hidden)
  .map((entry) => ({ ...entry.metadata }));
```

N 个技能 × 每次调用(每次 processNormalRequirement 一次)。

**修复建议**:
- 缓存 immutable snapshot,只在 scanSkills / rescanSkill 时失效

## 4. 🔧 可维护性 / 健壮性

### 4.1 [High] `setExecutor()` 注释与实现不一致

**位置**: `src/task-queue/index.ts:54-65`

注释说 "executor 跟随 task 生命周期";实际仍保留 `setExecutor()` 实例级方法,且 TaskGraphExecutor 在 addTask 时绑定 `task.executor`(P3 race fix)。两套机制并存,容易误用。

**修复建议**:
- 删除 `setExecutor()`,只保留 per-task 绑定
- 或保留 setExecutor 但废弃 P3 fix(场景不明确)

---

### 4.2 [High] `IntentRouter.classify` 接受 8 个位置参数,无 options bag

**位置**: `src/routers/intent-router.ts:73-82`

```typescript
async classify(
  userInput: string,
  userProfile?: UserProfile,
  recentHistory?: ...,
  sessionId?: string,
  _proceduralExperience?: ...,
  _userId?: string,
  persona?: PersonaConfig,
  displayName?: string,
)
```

8 个参数,前两个 unused(`_proceduralExperience`, `_userId`),调用方极易传错位置。

**修复建议**:
```typescript
async classify(opts: {
  userInput: string,
  userProfile?: UserProfile,
  recentHistory?: ...,
  sessionId?: string,
  persona?: PersonaConfig,
  displayName?: string,
})
```

### 4.3 [High] `CONFIG` 在 `src/types/index.ts` 顶部执行 `dotenv.config()`

**位置**: `src/types/index.ts:571-651`

```typescript
dotenv.config({ path: resolveResource('.env') });
export const CONFIG = { ... }
```

**问题**:
- `dotenv.config` 是副作用,类型模块导入即触发
- 测试环境可能不希望加载 .env(避免污染)

**修复建议**:
- `CONFIG` 改为函数 `loadConfig()` 返回
- 或显式 `bootstrap()` 中调用 `dotenv.config()` 后再 import types

**修复建议**:
- 拆出 `executeLayer(layer, ...)` 和 `onLayerResult(layerResults, ...)` 辅助函数

### 4.6 [Medium] 错误信息混入中文与英文,前端展示不一致

`src/api/index.ts` `BusinessError` message 多为英文(如 `"Failed to start server"`),但 `MainAgent` 业务错误 message 多为中文(如 `'抱歉，这个问题暂时超出了我的处理范围'`)。前端 i18n 处理困难。

**修复建议**:
- 统一 `code` + `message` 分开: code 给机器判断(message key),message 给开发者,前端做翻译

### 4.7 [Medium] `MemoryService.popLastAssistantMessage` 重写 L4 但不留审计

**位置**: `src/memory/memory-service.ts:191-216`

删除最后一条 assistant message 是 `needs_intent_reclassification` 路径,但当前 L4 文件直接覆盖,无审计 / 撤销能力。

**修复建议**:
- 移到 `deletes` 数组而非真实删除
- 或保留最近 N 条 `tombstones` 供恢复

---

### 4.8 [Medium] SSE 事件 buffer 可能被丢弃

**位置**: `src/api/index.ts:464-487`

lifecycle / task / reasoning 事件在 flushHeaders 之前入 buffer,**但 gate queued / queueFull 路径直接 discard**。如果用户的请求被排队后被 drain 到 R2,R2 的 lifecycle 事件对原 SSE 不可见。

**修复建议**:
- 排队时记录"原始 stream 已 close",R2 完成时重新开启 SSE(类似 `request_error` 的处理)
- 或在 JSON 响应中携带 `redirect-to-stream` 链接
