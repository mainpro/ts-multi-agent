## 3. 进程架构

### 3.1 单进程角色:多员工并存

**单进程 = 多员工并存**。所有 enabled 的员工在启动期一次性加载到 `EmployeeRegistry`,运行期只读。
- 进程内持有 1 个 `MainAgent` + 1 个 `EmployeeRegistry`(N 个 `EmployeeAgent`)+ 1 个共享 `SubAgent` 实例 + 1 套记忆 + 1 个 `SkillRegistry`
- 每个 `EmployeeAgent` = `EmployeeConfig`(JSON)+ 内部 `SubAgent`(每次 `executeSubTask` 临时构造),persona/tools/skills/rewriter 由 EmployeeAgent 持有,MainAgent 通过 registry 按 `task.employeeId` 派发
- `IntentRouter.classify()` 一次 LLM 调用同时返回 `intent` + `employeeId`(零额外 LLM);`routeIntentToEmployee()` 路由到对应员工,缺失/不存在 → 静默兜底到 `fallback-service-desk`
- 多实例部署 = 起多个进程,每个进程持各自的 registry(可用 `--employees-dir` 指向不同子目录)

### 3.2 Bootstrap 流程

`src/index.ts:68-205`:

```
1. dotenv.config() 加载 .env
2. buildFallbackLLMClient() 创建 LLM 客户端(fallback 链)
3. SkillRegistry().scanSkills() + startWatch() 扫描技能
4. MemoryService(DATA_DIR, llm) 创建 4 层记忆
5. SubAgent(skillRegistry, llm, memory) 共享执行器(无 persona,persona 由 EmployeeAgent 注入)
6. TaskQueue(executor) 创建任务队列
7. MainAgent 依赖注入:IntentRouter / UserProfileService / DynamicContextBuilder /
   SessionStore / AskAgent / SystemSkillLoader / ExecutorRegistry
8. loadAllEnabledEmployees({ directory, deps }) 读 employees/*.json,逐个构造
   EmployeeAgent 并 register 到 EmployeeRegistry;校验 fallback-service-desk 存在
   且 enabled(否则 BootstrapError, fail-fast)
9. MainAgent(deps) 创建主智能体(持有 EmployeeRegistry)
10. createAPIServer() Express 应用,监听 PORT
```

异常处理: 任何步骤失败抛 `BootstrapError`,由 `globalErrorHandler` 统一转为 500。

### 3.3 多员工并存:加载策略

`src/agents/employee/all-loader.ts:35-109`:

- 遍历 `--employees-dir`(`src/index.ts:154`)或 `resolveResource('employees')` 下所有 `*.json`(按文件名排序)
- 每个文件: `parseEmployeeConfig`(Zod 校验)+ `enabled !== false` 才 register;校验失败只 warn 跳过(`DUPLICATE_EMPLOYEE` 是 fail-fast)
- 加载完成必须满足:
  - `registry.list().length > 0`(否则 `NO_EMPLOYEE_CONFIG`)
  - `registry.defaultFallback()` 必须能拿到 `fallback-service-desk` 且 enabled(否则 `FALLBACK_EMPLOYEE_MISSING` / `FALLBACK_EMPLOYEE_DISABLED`)
- `--employees-dir` 是测试 + 多租户场景的扩展点,生产部署通常指向内置 `employees/`

### 3.5 多员工并存:路由与派发

单进程多员工的关键是**路由**(选哪个员工)和**派发**(任务归属哪个员工执行)。两者贯穿整个请求生命周期。

**路由(`routeIntentToEmployee`)**

```
IntentRouter.classify() 输出 IntentResult
    ├─ employeeId 存在 && registry.has(employeeId) → registry.get(employeeId)
    ├─ employeeId 不存在 / undefined              → registry.defaultFallback()
    └─ employeeId 存在但 registry.has(...) === false → log.warn + registry.defaultFallback()
```

`src/agents/employee/router.ts:17-32`。该函数**永不抛错**,保证主路径不会因 employeeId 异常而崩溃。

**派发(`Task.employeeId` + `TaskGraphExecutor`)**

每个 runtime `Task` 携带 `employeeId`(由 IntentRouter / Planner 注入)。`TaskGraphExecutor.executeLayers` 在 `addTask` 时按 `task.employeeId` 从 registry 取对应 EmployeeAgent(`src/agents/task-graph-executor.ts`),EmployeeAgent 内部临时构造 SubAgent 执行。

**汇总(`ResultAggregator`)**

汇总阶段按 `task.employeeId` 在 registry 拿每个任务的 `resultRewriter`,逐 task 应用(`src/agents/result-aggregator.ts:54-63`)。如果 task 的 `employeeId` 在汇总时已不在 registry(理论上不可能,防御编程),rewriter 静默跳过。

**关键不变量**

| 项 | 保证 |
|---|---|
| 注册表运行期只读 | `EmployeeRegistry.register` 仅在 bootstrap 调用一次,运行期不修改 |
| 兜底员工始终可用 | `EmployeeRegistry.defaultFallback()` 启动期校验,失败 fail-fast |
| 每个 task 都有 employeeId | Planner / IntentRouter 必须填,缺失时 MainAgent 兜底注入 fallback |
| 跨员工 task 依赖 | 同一 Request 内不同 employeeId 的 task 可在 task 图中共存,各自独立路由 |

### 4.4 关键路径:Steer 注入

```
触发: session 有 activeRequest 且至少 1 个 task.status === 'running'

[API 层] /tasks/stream
    ├─ mainAgent.shouldSteer(userId, sessionId)
    │   └─ 检查 activeRequest.status === 'processing' + 有 running task
    ├─ 若 true → steeringBuffer.enqueue({content, enqueuedAt})
    └─ 返回 202 {steered: true}

[SubAgent 工具循环] 每轮 LLM 调用前
    ├─ consumeSteering(sessionId) → messages.push({role: user, content})
    └─ emit request_steered event (SSE 通知前端)
```

**关键**: 仅在 active request 有 running task 时 steer,否则回退到 gate 队列(steer 无人消费会丢失)。

## 5. 数据契约

### 5.1 核心类型(摘选)

`src/types/index.ts` 是类型中枢:

```typescript
// Task 是运行时任务对象
interface Task {
  id: string;
  requirement: string;
  skillName?: string;
  status?: 'pending' | 'running' | 'completed' | 'failed' | 'suspended' | 'waiting';
  result?: TaskResult;
  error?: TaskError;
  params?: Record<string, unknown>;
  dependencies: string[];
  dependents?: string[];
  sessionId?: string;
  userId?: string;
  conversationContext?: Message[];  // LLM 上下文(断点续传)
  completedToolCalls?: CompletedToolCall[];
  executor?: TaskExecutor;          // per-task 绑定(P3 race fix)
  _personaContext?: PersonaContext; // Master 注入的 persona
  allowedTools?: string[];          // Master 注入的工具列表
}

// TaskPlan 是 LLM 规划输出
interface TaskPlan {
  id: string;
  requirement: string;
  tasks: Array<{
    id: string;
    requirement: string;
    skillName: string;
    params?: Record<string, unknown>;
    dependencies: string[];
    _personaContext?: PersonaContext; // 由 MainAgent 注入(派单前)
    allowedTools?: string[];          // 由 MainAgent 注入(派单前)
  }>;
}

// TaskGraph 是拓扑排序后的 DAG
interface TaskGraph {
  id: string;
  requirement: string;
  nodes: TaskGraphNode[];
  layers: string[][];  // layers[i] = 第 i 层可并行执行的任务
}

// Request 是 session 内的一个用户请求
interface Request {
  requestId: string;
  content: string;
  status: RequestStatus;
  tasks: RequestTask[];          // 持久化的 task 副本
  questions: QAEntry[];          // 主智能体问题
  result: string | null;
  executionProgress?: ExecutionProgress; // 断点续传用
}

// Session 是用户级会话
interface Session {
  userId: string;
  sessionId: string;
  requests: Request[];
  activeRequestId: string | null;
  pendingRequests: PendingRequest[];  // checkpoint 合并队列
}
```

### 5.5 状态机

#### Request 状态机
```
[New] → processing ──┬─→ waiting (ask_user 挂起)
                      ├─→ completed (所有 task 完成 + 汇总完成)
                      ├─→ failed (致命错误)
                      └─→ checkpoint_reached (R1 让位给 R2)

waiting → processing (用户回答问题)
completed/failed → 终态
```

#### Task 状态机
```
[New] → pending → running → completed
                   ├─→ failed (skill 抛错 / 超时)
                   ├─→ waiting (ask_user 挂起) → pending (用户回答)
                   └─→ suspended (会话挂起) → pending (会话召回)
```

`Task.employeeId?: string`(`src/types/index.ts`)由 IntentRouter / Planner 注入,TaskGraphExecutor 据此派发到对应 EmployeeAgent 执行。

## 6. 持久化设计

### 6.1 文件布局

```
data/
└── memory/
    ├── {userId}/
    │   ├── profile.json                  # L2 用户档案
    │   ├── session/{sessionId}.json      # SessionStore(状态机)
    │   ├── history/{sessionId}.json      # L4 完整历史
    │   └── summaries/{sessionId}.json    # L3 请求摘要
```

### 6.2 SessionStore 写入策略

- **默认防抖 100ms** 写盘(`saveSession`)
- **特殊情况立即刷盘**(`flushToDisk`): waiting 状态、pending queue 入队/出队、executionProgress 完成态
- **启动清理**: `cleanupStaleSessions()` 扫所有 session,把 dangling / processing >0 的 active request 修正
- **内部字段过滤**: `stripInternalFields` 当前是 identity(确保 `pendingRequests` 等关键字段不被丢弃)

### 6.3 4 层记忆

| 层 | 存储 | TTL | 内容 | 用途 |
|---|---|---|---|---|
| **L1** | 内存 Map | 30min | conversation[] + pendingRequestSummary | 会话级快速上下文 |
| **L2** | JSON 文件 | 永久 | profile + preferences + history | 跨会话用户画像 |
| **L3** | JSON + embedding | 30d | requestSummaries + sessionSummaries | 语义召回 |
| **L4** | JSON 文件 | 永久 | 完整 history entries | 进程重启后恢复 |

**写一致性**:
- L1 + L4 **同步双写**(`saveUserMessage` / `saveAssistantMessage`)
- L3 摘要**异步生成**,失败不阻塞主流程(`summarizeRequest` 包 fire-and-forget)
- L2 增量更新(`updateProfile`)

## 7. 关键算法

### 7.1 DAG 拓扑分层(`TaskGraphExecutor.buildTaskGraph`)

```typescript
1. 对每个 node:
   - inDegree[taskId] = dependencies.length
   - dependents[taskId] = []

2. 拓扑排序:
   while processed.size < nodes.length:
     ready = nodes.filter(n => !processed && inDegree[n] === 0)
     if ready.empty: 剩余节点放入同一层(检测到环的兜底)
     layers.push(ready)
     for n in ready:
       processed.add(n)
       for d in dependents[n]:
         inDegree[d]--

3. 返回 {layers: string[][]}
```

**复杂度**: O(V + E),V = tasks, E = dependencies。

### 7.2 工具 3 段过滤(`EmployeeAgent.computeAllowedTools`)

`src/agents/employee/agent.ts:103-105` + `src/agents/employee/tools.ts`:

```typescript
1. baseSet = skill.allowedTools ?? DEFAULT_SAFE_TOOLS
2. if employee.tools.enabled:
     baseSet = baseSet ∩ enabled
3. if employee.tools.denied:
     baseSet = baseSet − denied
4. 返回 baseSet (Set<string>)
```

**关键差异**:
- `task.allowedTools !== undefined` 优先于 skill.allowedTools(Task 7 安全 fix: 避免 `[]` 被当成 "未设置")
- 员工黑名单**最高优先级**(即使 enabled 通过也会被剔除)
- 计算时机:`EmployeeAgent.executeSubTask` 入口处计算,结果写入 `task.allowedTools` 透传给 SubAgent

### 7.3 Pending 队列合并(`SessionGate + spawnMergedRequest`)

```typescript
触发: onCheckpoint 检测到 session.pendingRequests.length > 0

合并算法:
  mergedContent = parent.content
  for p in drain():
    mergedContent += '\n---\n\n' + p.requirement

限制: MAX_PENDING_REQUESTS = 10(LLM 上下文保护)
```

### 7.4 工具调用拆分(`LLMClient.generateWithTools`)

```typescript
每轮 LLM 调用后:
  safeCalls = tool_calls.filter(c => concurrencyChecker(c.name, c.args))
  unsafeCalls = tool_calls.filter(c => !concurrencyChecker(c.name, c.args))

  safeCalls → Promise.allSettled (并行)
  unsafeCalls → for-await (串行)

  concurrencyChecker 规则: DEFAULT_SAFE_TOOLS.has(name)
  // safe: read / glob / grep / conversation-get / ask_user / append_improvement
  // unsafe: write / edit / bash
```

### 7.5 CONTEXT_TOO_LONG 压缩(`SubAgent.executeSkill`)

```typescript
while attempts <= 1:
  try:
    return llm.generateWithTools(messages, ...)
  except LLMError('CONTEXT_TOO_LONG') and attempts < 1:
    messages = compactMessages(messages, llm, {tokenBudget: 8000, keepRecent: 5})
    attempts++

// 不可达:循环要么 return 要么 throw
```

`compactMessages` 通过 LLM 总结早期 tool_result + 保留最近 5 条消息,把 token 数压到 8000 以内。

## 8. 安全设计

### 8.1 三层防御

| 层 | 实现 | 作用 |
|---|---|---|
| **路径白名单** | `PathGuard.checkPath` 解析 realpath,校验必须在 workDir 内 | 防止 read/write 越权 |
| **路径黑名单** | regex 拦截 .ssh / .aws / .env / .pem / .key 等 | 防止访问凭据 |
| **Bash 命令白名单** | 只允许已知前缀(node scripts/, npm, ls 等) | 防止 shell 注入 |
| **Bash 危险模式黑名单** | sudo / eval / `...` / $(...) / rm -rf / 等兜底 | 防止命令替换 |

### 8.2 Guardrail 中间件

`src/guardrail/`:
- 关键词规则 + PII 检测(`pii-patterns.ts` 识别身份证/手机/邮箱)
- 用户角色 + 权限矩阵(`role: 'employee'` 默认无 privileged)
- 三档决策:**deny** (拒绝) / **rewrite** (改写) / **alert** (放行但审计)

### 8.3 错误分类(`errors/`)

```
AppError (基类,带 type/code/statusCode/cause)
├── LlmError (LLM 调用错误,继承 LLMError type)
├── SkillError (技能执行错误)
├── BusinessError (业务规则错误)
├── ConfigError (配置错误)
└── BootstrapError (启动错误)
```

所有 AppError 在 TaskGraphExecutor 保留 `originalError`,最终由 globalErrorHandler 转为 HTTP 响应,type/code 不丢失。

## 13. 已落地:失败重试 + 部分汇总(2026-08-14)

参考 spec `docs/superpowers/specs/2026-08-14-partial-failure-retry-design.md`。

### 13.1 重试循环(TaskQueue)

`src/task-queue/index.ts` 的 `executeTask` 改为带退避的重试循环:

- 默认 `maxRetries=2`(Task 字段,可由 `employee.execution.maxRetries` 覆盖)
- 默认仅重试 LLM 临时错:`TIMEOUT` / `NETWORK_ERROR` / `API_ERROR` 且 `statusCode >= 500`
- 重试退避:base 2s, factor 2, max 60s, ±1s jitter(可通过构造函数 `retryBackoff` 参数测试覆盖)
- 同时识别 `LLMError`(直接)和 `LlmError`(SubAgent `mapSubAgentError` 包出来的)— 后者是生产路径

### 13.2 失败语义(TaskGraphExecutor + MainAgent)

`executeTaskGraph` 区分两种失败模式(spec §7.1):

| 场景 | 行为 |
|---|---|
| **全 task 都 failed** | `throw` SkillError(保留 `AppError` original cause),走原 catch 路径,API 返回 4xx/5xx |
| **部分 failed(有成功)** | `return { success: false, data: { hasPartialFailure: true, failedTasks } }`,MainAgent 走汇总路径 |
| **全 succeeded** | `return { success: true }`(原路径) |

### 13.3 混合状态汇总(ResultAggregator)

`summarizeResults` 重写支持混合 status:

- 拆分 `completedTasks` / `failedTasks` / `waitingTasks`
- LLM 看到全部 task 状态,生成诚实摘要("X 成功, Y 失败")
- **B-1 真正的修法**:rewriter gate 用 `every(completed)` 而非 `taskResults[0]?.status` 或 `taskResults[N-1]?.status`
- **防御纵深**:有 failedTasks 时强制 `completed=false`,即使 LLM 误判
- **Transfer hook**:`TransferToHumanHook = (TaskResult[]) => boolean`,默认 noop,本期未接外部工单系统

### 13.4 Request 状态机扩展

- `Request.status === 'completed'` 语义保持("请求结束")
- `Request.partialFailure?: boolean` 标志区分纯成功 vs 部分失败
- `Request.failedTaskIds?: string[]` 给前端展示
- `SessionStore.completeRequest` 加可选第 5 参数 `{ partialFailure?, failedTaskIds? }`,**`partialFailure=true` 时跳过 `syncRequestStatus` 强制 `status='completed'`**

### 13.5 Feature Flag

`CONFIG.PARTIAL_FAILURE_ENABLED`(默认 `true`):
- `false` 时退退化为旧 throw 路径
- 通过 `process.env.PARTIAL_FAILURE_ENABLED !== 'false'` 解析

## 14. 已落地:单进程多员工并存(2026-08-18)

参考 spec `docs/superpowers/specs/2026-08-17-multi-employee-sub-agent-design.md`。

### 14.1 EmployeeAgent(`src/agents/employee/agent.ts`)

数字员工 = `EmployeeConfig` + 内部 `SubAgent` 实例的封装:
- 只读 getters:`id` / `displayName` / `isEnabled` / `persona` / `personaPrefix`(已替换 `${displayName}`)/ `decompositionHint` / `maxParallelTasks` / `execution` / `resultRewriter`
- `isSkillAllowed(skillName)`: 校验 skill 在白名单(`allowlist` 模式)或 `unrestricted` 模式放行
- `computeAllowedTools(skillAllowedTools)`: 3 段过滤 = skill ∩ employee.enabled − employee.denied
- `executeSubTask(task, context)`: 每次构造新 SubAgent(task 上下文独立,P3 race fix 模式);skill 白名单失败抛 `SkillError('SKILL_NOT_ALLOWED')`

### 14.2 EmployeeRegistry(`src/agents/employee/registry.ts`)

进程级员工注册表:
- `register(agent)`: 启动期一次性调用,重复 id 抛 `BootstrapError('DUPLICATE_EMPLOYEE')`
- `get(id)` / `has(id)` / `list()`(仅 enabled)/ `listForLLM()`(给 IntentRouter prompt)
- `defaultFallback()`: 返回 `fallback-service-desk`;缺失或 disabled 抛 `BootstrapError('FALLBACK_EMPLOYEE_MISSING' / `'FALLBACK_EMPLOYEE_DISABLED')`,启动 fail-fast

### 14.3 路由(`src/agents/employee/router.ts:17-32`)

`routeIntentToEmployee(intentResult, registry)`:
- `employeeId` 存在 + `registry.has` → `registry.get`
- 否则 / 不存在 → `log.warn`(LLM 返回不存在 id 时)+ `registry.defaultFallback()`
- **永不抛错**,保证主路径不会因 employeeId 异常崩溃

### 14.4 IntentRouter 扩展(`src/routers/intent-router.ts:159-165`)

LLM 返回 `IntentResult.employeeId?: string`,与 `intent` / `tasks` 在同一次 `llm.generateStructured` 调用中产出,**零额外 LLM 调用**。`availableEmployees` 参数在 prompt 里列出 `{id, brief}` 让 LLM 选。

### 14.5 派发与汇总

- `Task.employeeId?: string`(`src/types/index.ts`): 运行时 task 携带员工身份
- `TaskGraphExecutor`: `addTask` 时按 `task.employeeId` 从 registry 取对应 `EmployeeAgent` 执行
- `ResultAggregator.summarizeResults`: 按 `task.employeeId` 逐 task 在 registry 拿对应 `resultRewriter`,逐 task 应用(不再是 process 级单一 rewriter)

### 14.6 启动集成(`src/index.ts:154-161` + `all-loader.ts`)

```
parseEmployeeDirArg(argv) 解析 --employees-dir=<path>
  → loadAllEnabledEmployees({ directory, deps: { llm, memory, session, skillRegistry } })
    → EmployeeRegistry.register(每个 enabled 员工)
    → registry.defaultFallback() 校验
  → mainAgent.employeeRegistry = registry
```

`enabled: false` 的 JSON 跳过 + warn;目录空 / 全 disabled / 兜底缺失都 fail-fast(`NO_EMPLOYEE_CONFIG` / `FALLBACK_EMPLOYEE_*`)。
